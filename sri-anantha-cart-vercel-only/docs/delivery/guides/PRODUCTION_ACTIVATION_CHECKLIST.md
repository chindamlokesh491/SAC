# Production Activation Checklist

**This is separate from staging.** Nothing in production is enabled by this delivery. Each item needs the named owner, and the final launch needs written approval.

## 1. Accounts owned by the client

- [ ] Supabase organisation and production project (Mumbai `ap-south-1`), owned by the client; engineer access via invitation
- [ ] Vercel team owned by the client; Pro billing on the client's card for commercial production and per-minute Cron
- [ ] Domain registrar and DNS access (`docs/deployment/DOMAIN.md`)
- [ ] Google Cloud project for OAuth (web + Android client IDs); consent screen verified
- [ ] Razorpay account: KYC complete; live keys generated by the client
- [ ] SMS Gateway Hub account; DLT registration (Principal Entity, header)
- [ ] Shiprocket, only if approved for a later phase
- [ ] Google Play Console (Android app) and signing keys under the client's account

## 2. Production database

- [ ] Fresh production database; migrations 001–037 applied by the release pipeline (owner role), development seed **not** applied
- [ ] Runtime role created (`database/roles/app_runtime_role.sql`); API and Vercel Cron worker use it
- [ ] Supabase security and performance advisors clean
- [ ] Point-in-time recovery enabled; **restore drill completed** into a scratch project
- [ ] Real catalogue, prices, GST/HSN, stock, delivery zones, fees and minimum orders entered and reviewed by the client

## 3. Configuration (dashboard secrets only)

- [ ] `DEPLOYMENT_ENV=production`, `NODE_ENV=production`, `ALLOW_DEV_OTP=false`
- [ ] `SESSION_SECRET`, `INTERNAL_API_TOKEN`, `REVALIDATE_TOKEN` generated fresh (never reuse staging values)
- [ ] `DATABASE_SSL_CA` set; TLS verification on
- [ ] SMS: `OTP_PROVIDER=smsgatewayhub` with the approved sign-in template, and preferably the delivery-code template
- [ ] One real OTP received on a test phone, and the provider message ID visible in `otp_challenges`
- [ ] Google client IDs for production origins

## 4. Payments (separate approval)

- [ ] Razorpay test-mode acceptance passed in staging (`docs/payments/RAZORPAY_TEST_ACCEPTANCE.md`)
- [ ] Live keys entered; `RAZORPAY_MODE=live`, `RAZORPAY_LIVE_APPROVED=true` (the API refuses live without both and `DEPLOYMENT_ENV=production`)
- [ ] Webhook configured to the production API with the live webhook secret; signature verified with a ₹1 live payment, then refunded
- [ ] Decide on `RAZORPAY_REFUNDS_ENABLED` (gateway refunds) after a refund test
- [ ] `ONLINE_PAYMENTS_ENABLED=true` only after the above

## 5. Security

- [ ] Penetration test or independent security review of the store, admin, partner PWA and API
- [ ] `pnpm audit --prod` reviewed (currently: no high or critical findings)
- [ ] Admin accounts: temporary passwords changed; staff list reviewed; partners provisioned without passwords
- [ ] Secrets rotated if they were ever shared outside dashboards

## 6. Monitoring and operations

- [ ] Uptime monitor on `/ready` (API) and store/admin home pages
- [ ] Error tracking (e.g. Sentry) for API and web apps, with PII scrubbing
- [ ] Log retention and alerting on 5xx rates, failed jobs (payment reconciliation), and SMS provider errors
- [ ] Database metrics (connections, slow queries) and storage usage alerts
- [ ] Runbooks:
  - SMS provider outage (customers can still read delivery codes in-app);
  - payment reconciliation;
  - `SESSION_SECRET` rotation (outside delivery hours);
  - restore from backup.

## 7. Recovery

- [ ] Documented RPO/RTO agreed with the client
- [ ] Restore drill result recorded (date, time taken, data verified)
- [ ] Application rollback procedure tested (redeploy the previous build; migrations are forward-only)

## 8. Maintenance

- [ ] Owner for dependency updates (monthly `pnpm audit`)
- [ ] Owner for the DLT template list and SMS balance
- [ ] Process for staff onboarding and offboarding (Settings → Staff; removal revokes sessions)

## 9. Launch approval

- [ ] Client acceptance sign-off (all scenarios in `CLIENT_ACCEPTANCE_TESTING.md`)
- [ ] All items above checked
- [ ] Written go-live approval from the client, with date and time
- [ ] `CHECKOUT_ENABLED=true` switched on at the agreed time
