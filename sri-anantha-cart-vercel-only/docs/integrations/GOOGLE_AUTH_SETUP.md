# Google Sign-In setup

Sri Anantha Cart already implements Google Identity Services for the customer website and Google ID-token sign-in for the Expo Android app. The Fastify API verifies the Google ID token and then creates the application's existing session (HttpOnly cookie on web, bearer token on mobile).

This project uses its own `users` and `auth_sessions` tables. **Do not enable a second, separate Supabase Auth login for this flow.** The app does not need a Google client secret: it only accepts signed ID tokens whose audience matches one of the configured Google OAuth client IDs.

## Google Cloud Console

Use one Google Cloud project for the web and Android OAuth clients. Configure the Google Auth Platform branding and audience. While the app is in testing, add the Google accounts that will test sign-in.

### 1. Create a Web application OAuth client

Add these Authorized JavaScript origins:

- `http://localhost:3000` (local web development)
- `https://sri-anantha-cart-storefront-staging.vercel.app` (current staging storefront)
- `https://sriananthacart.in` (add when the production custom domain is active)

The current web implementation uses the Google Identity Services credential callback, not an OAuth redirect endpoint. Do not add a Supabase callback URL for this flow.

Save the **Web Client ID**. Do not send or store the generated client secret; this implementation does not use it.

### 2. Create an Android OAuth client

Use the Android package name:

```text
in.sriananthacart.app
```

Google requires the SHA-1 fingerprint for the Android signing certificate. Register the fingerprints for the certificates that will sign the builds you test:

- Local debug keystore, for local/debug builds.
- EAS Android keystore, for EAS preview/production builds.
- Google Play App Signing certificate, once Play App Signing is configured (use the app-signing certificate, not just the upload certificate).

Save the **Android Client ID**. If debug and release use different certificates, register each certificate/package pair in Google Cloud.

## Runtime configuration

After the client IDs are created, set these values. OAuth client IDs are public identifiers, not secrets.

| Platform | Variable | Value |
|---|---|---|
| Render active API service | `GOOGLE_CLIENT_IDS` | `<WEB_CLIENT_ID>,<ANDROID_CLIENT_ID>` |
| Vercel storefront project | `NEXT_PUBLIC_GOOGLE_CLIENT_ID` | `<WEB_CLIENT_ID>` |
| EAS preview build | `EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID` | `<ANDROID_CLIENT_ID>` |
| EAS preview build | `EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID` | `<WEB_CLIENT_ID>` |
| EAS production build | same two `EXPO_PUBLIC_*` variables | same respective IDs |

For initial web-only activation, the Web Client ID alone is sufficient: set `GOOGLE_CLIENT_IDS=<WEB_CLIENT_ID>` in the Vercel API project's environment and `NEXT_PUBLIC_GOOGLE_CLIENT_ID=<WEB_CLIENT_ID>` in the storefront/admin Vercel projects. Add the Android ID and EAS variables when the Android signing fingerprint is ready.

The connected Vercel project is specifically the **staging storefront** (`sri-anantha-cart-storefront-staging`). Its Vercel Production target is the canonical main-branch staging deployment, not the separate customer-facing production system. Set `NEXT_PUBLIC_GOOGLE_CLIENT_ID` on that Production target only: autogenerated PR Preview URLs are different origins and are not authorized by the current Google OAuth client. For local development, put the same client ID in the ignored storefront `.env.local` file; `http://localhost:3000` is already an authorized origin. After changing the variable, redeploy the staging storefront because `NEXT_PUBLIC_*` values are compiled into the browser bundle. The admin app does not use customer Google sign-in.

## Existing customer accounts

Google sign-in identifies an account by Google's stable `sub` claim. It deliberately does not merge accounts based only on matching email addresses. Customers who already use mobile OTP should sign in with their phone first, then link Google from **Account → Settings**. This prevents an unverified email on an existing profile from being used to take over that account.


## EAS environment variables

The repository's EAS profiles explicitly select their matching environments:

- `preview` build profile → EAS `preview` environment and the staging API/storefront URLs
- `production` build profile → EAS `production` environment and the production API/storefront URLs

Build the preview APK for staging acceptance tests; do not use the production profile until the production OAuth origin and production rollout are ready. The preview app uses the verified Vercel staging hostname for its App Links host. Android App Links verification is a separate setup: after the preview signing certificate is known, set the matching SHA-256 fingerprint in the storefront's server-side `ANDROID_CERT_SHA256` variable so `/.well-known/assetlinks.json` can return the correct association. This SHA-256 fingerprint is separate from the SHA-1 fingerprint used to create the Android OAuth client.

After creating the Google Android client, run these commands from `apps/mobile` (replace the placeholders with the public OAuth client IDs):

```bash
eas env:set --name EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID --value "<ANDROID_CLIENT_ID>" --environment preview --visibility plaintext
eas env:set --name EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID --value "<WEB_CLIENT_ID>" --environment preview --visibility plaintext
eas env:set --name EXPO_PUBLIC_GOOGLE_ANDROID_CLIENT_ID --value "<ANDROID_CLIENT_ID>" --environment production --visibility plaintext
eas env:set --name EXPO_PUBLIC_GOOGLE_WEB_CLIENT_ID --value "<WEB_CLIENT_ID>" --environment production --visibility plaintext
```

These values use `plaintext` visibility because they are public OAuth client IDs embedded in the mobile app. They are not secrets. Never store a Google client secret, keystore, or keystore password in an `EXPO_PUBLIC_*` variable.

For local Android development, use an ignored local `.env` file with the same two `EXPO_PUBLIC_*` names and the appropriate local/debug client IDs. Do not commit the `.env` file.

## Verification checklist

1. Test a new Google account on the staging storefront.
2. Confirm a session is created and survives a page reload.
3. Test an existing OTP customer linking Google from Account Settings.
4. Confirm an unverified Google email is rejected and a Google identity cannot be attached to two customer profiles.
5. Build the Android preview app with the Android and Web Client IDs, then test sign-in on a physical Android device.
6. Confirm staff accounts continue using staff password sign-in; Google is customer-only.
